# Flow Momentum: спецификация

Версия 1 от 30.09.2026: веса проверены на сезоне АПЛ (раздел 8). Это спецификация для Flow Engine. Числа, которые обещает мокап, взяты из `design/mockup/Match.dc.html`.

## 1. Что видит пользователь

| На экране | Откуда берётся |
|---|---|
| `MCI 82` · `ARS 37` | `Flow` каждой команды, шкала 0–100 (не ниже ≈15, раздел 3), считаются независимо (сумма ≠ 100) |
| `▲ +18 за 10′` | `Flow(t) − Flow(t − 10 мин)` |
| Доля потока за 10 минут | `Flow_home / (Flow_home + Flow_away)` |
| Волна, окна 1 / 5 / 15 мин | `wave = Flow_home − Flow_away` ∈ [−100, 100], скользящее среднее по окну |
| Хроника: Flow-эффект события | вес события `w(e)` |
| Explainability: факторы | вклады событий в текущий `S` (раздел 6) |

## 2. Входные данные

Нормализованное событие (одинаковое для всех источников):

| Поле | Тип | Пример |
|---|---|---|
| `type` | enum | `goal`, `shot_on_target`, `shot_off_target`, `shot_blocked`, `corner`, `yellow_card`, `red_card`, `substitution`, `foul`, `offside`, `take_on`; внутренние, без показа в хронике: `key_pass` (пас, после которого был удар), `tackle` |
| `team` | `home` / `away` | команда, совершившая событие |
| `t` | минуты, float | `72.23` |
| `x`, `y` | 0–100 | атака всегда слева направо, ворота соперника в точке `x = 100` |
| `bodyPart` | `right_foot` / `left_foot` / `head` / `other` | удары |
| `situation` | `open_play` / `free_kick` / `penalty` / `corner` / `cross` | удары |
| `xG` | float или `null` | StatsBomb отдаёт готовый; для ESPN считаем сами (раздел 5) |

Источники: ESPN `commentary[].play` (`type.text`, `clock`, `fieldPositionX/Y`, `text`), StatsBomb events. Сопоставление полей описано в коде нормализатора.

Кроме событий нужно **владение по минутам** `p_team(m)`: доля мяча у команды за минуту `m`, число от 0 до 1.

- **ESPN** отдаёт владение только **нарастающим итогом** с начала матча (`boxscore` → `possessionPct`). Долю за интервал между двумя опросами можно восстановить, потому что итог — это среднее, взвешенное по времени:

  ```
  p[t1, t2] = (P(t2) · t2 − P(t1) · t1) / (t2 − t1)
  ```

  Здесь `P(t)` — нарастающее владение в момент `t` (игровое время). Если из 60 минут у команды было 55%, а к 61-й стало 55.3%, то за эту минуту у неё было `(0.553 · 61 − 0.55 · 60) / 1 ≈ 73%`.
- **StatsBomb**: у каждого события есть поле `possession_team`, и по времени между событиями доля за минуту считается напрямую.

## 3. Формула

**Импульс команды** — сумма затухающих вкладов её событий и её владения. Между событиями он затухает, а каждое событие добавляет свой вес, но не опускает импульс ниже нуля:

```
S_team ← S_team · exp(−Δt / τ)          между событиями
S_team ← max(0, S_team + w(e))          на событии
```

Владение работает как **событие, которое случается каждую минуту**: его вес `w_p · (p_team(m) − 0.5)` пропорционален тому, насколько доля мяча отклонилась от 50%. При 70% команда получает `+0.2 · w_p` за минуту, соперник со своими 30% — `−0.2 · w_p`, то есть его импульс гасится. Дальше владение затухает так же, как события: сразу и одной формулой.

**Flow** — импульс вместе с фоновым `S₀`, сжатый в 0–100:

```
Flow_team(t) = 100 · (1 − exp(−(S₀ + S_team(t)) / k))
```

**Волна:**

```
wave(t) = Flow_home(t) − Flow_away(t)
```

Зачем так:
- **Затухание вместо окна.** У окна есть обрыв: событие целиком влияет на Flow, а потом в одну секунду исчезает. Затухание убирает скачки без причины на поле.
- **`max(0, …)` на каждом событии.** Отрицательные веса (своя замена, чужое владение) только гасят накопленный импульс и не оставляют долга. Если бы импульс мог уйти в минус, после 20 минут без мяча команде пришлось бы «отыгрывать» долг, и её удары какое-то время вообще не отражались бы на Flow.
- **Фоновый импульс `S₀`.** Команда на поле всегда играет, поэтому её Flow не падает до нуля: минимум `100 · (1 − e^(−S₀/k)) ≈ 15`. `S₀` не затухает и не делится в перерыве. В волне он сокращается: у обеих команд одинаковый фон.
- **Насыщение.** Flow никогда не превышает 100. Первые события поднимают его быстро, дальнейшее давление — всё медленнее.

### 3.1 Перерыв

`t` — это **игровое** время, поэтому в перерыве затухание стоит. В начале второго тайма (и дополнительного времени) импульс частично сбрасывается:

```
S_team ← r · S_team,   r = 0.7
```

После перерыва игра начинается во многом заново, но преимущество первого тайма не исчезает полностью. `r` не подбирается по данным: это часть определения momentum (раздел 8).

## 4. Параметры v1

| Параметр | Значение | Смысл |
|---|---|---|
| `τ` | 5 мин | через 5 мин от импульса остаётся 37%, через 15 мин — 5% |
| `k` | 18.7 | масштаб. Факторы Explainability на мокапе в сумме дают `S = 29` (+14 +9 +7 +4 −5), с фоном `S₀ + S = 32`, и при `k = 18.7` получается `Flow ≈ 82`, как у Сити на экране |
| `S₀` | 3 | фоновый импульс: пол Flow ≈ 15 |
| тик пересчёта | 5 с | затухание идёт и без новых событий |
| `w_p` | 9 | вес владения за минуту на единицу отклонения от 50% |
| `r` | 0.7 | доля импульса, которая остаётся после перерыва (раздел 3.1) |

`w_p` выведен из фактора мокапа «Владение выросло с 51% до 68%: +9». Если команда стабильно владеет мячом с перевесом `Δp`, её вклад в `S` выходит на уровень `w_p · Δp / (1 − e^(−1/τ)) ≈ 5.5 · w_p · Δp`. При `Δp = 0.18` и вкладе +9 получается `w_p ≈ 9`.

Веса v0 были взяты из хроники мокапа. v1 — это v0 с тремя правками, которые проверка на сезоне нашла устойчивыми (раздел 8):

| Событие | Кому | `w` | Откуда |
|---|---|---|---|
| `goal` | забившей | +23 | мокап, оставлен сознательно (раздел 8) |
| удар (`shot_*`) | ударившей | `6 + 7.3 · xG` | мокап |
| `key_pass` | отдавшей | **+10** | проверка: было 0 |
| `yellow_card` | **сопернику** получившего | +5 | мокап |
| `red_card` | **своей**, оставшейся в меньшинстве | **−18** | проверка: было 0 |
| `corner` | подающей | +4 | мокап |
| `substitution` | сделавшей | **+5** | проверка: было −3, знак был неверным |
| `foul`, `offside`, `take_on`, `tackle` | — | 0 | проверка: вклад мал или неустойчив |

Формула веса удара выведена из двух точек мокапа: xG 0.41 → +9, xG 0.18 → +7.

## 5. Своя модель xG (для ESPN)

У ESPN xG нет, но у каждого удара есть координаты и описание. Модель:

- **Признаки:** расстояние до центра ворот, угол обзора ворот (оба по `x`, `y`), `bodyPart`, `situation`.
- **Данные для обучения:** все удары из StatsBomb Open Data. Их координаты (поле 120 × 80) переводятся в шкалу ESPN 0–100, а целевая переменная — был ли гол.
- **Модель:** логистическая регрессия. Её легко объяснить, и её результат — это просто набор коэффициентов.
- **Где считается:** обучение идёт в Python (AI Orchestrator), а коэффициенты экспортируются в JSON. Flow Engine на Go считает xG сам, без сетевого вызова: для логистической регрессии это одна формула.
- **Проверка:** на отложенных матчах StatsBomb сравнить с их xG (log loss, калибровочная кривая).
- **Если координат нет:** фиксированный вес удара `6 + 7.3 · 0.1`.

## 6. Explainability

`S` — это сумма вкладов событий, поэтому для любого момента можно перечислить события с наибольшим текущим вкладом `w(e) · exp(−(t − t_e)/τ)` и сгруппировать их («4 удара за 7 минут: +14»). Explainability Agent получает этот список и превращает его в текст, но ничего не придумывает сам.

## 7. Скачки и уведомления

Скачок — это когда `Flow(t) − Flow(t − 10 мин) ≥ порог`. Порог каждый пользователь задаёт в настройках. Notification Service дедуплицирует скачки: один скачок — одно уведомление.

## 8. Проверка на сезоне

Код в `ai/calibration/`, результат последнего прогона — `ai/calibration/report.json`.

**Вопрос.** Ударит ли команда в ближайшие 10 минут? Удар — любое событие с xG (автогол ударом не считается). Для каждой команды и каждой минуты берём Flow в эту минуту и ответ, связанные логистической функцией `P = sigmoid(a + b · Flow / 100)`. Минуты, после которых до конца тайма меньше 10 минут, не используются.

**Данные.** АПЛ 2015/16 из StatsBomb Open Data: 380 матчей, 57 656 «команда-минут», удар в следующие 10 минут в 71% случаев. События проходят через тот же нормализатор, что и живой реплей (`services/cmd/export`). Python-версия Flow совпадает с Go-движком до 10⁻¹³ на всех минутах сезона (`parity.py`).

**Как проверяли.** Сезон режется по датам на 5 блоков. Каждый блок предсказывает модель, обученная на остальных четырёх, так что каждый матч предсказан моделью, которая его не видела. Интервалы — бутстрэп по матчам (2000 выборок): минуты одного матча зависимы, матчи — нет. Модели сравниваются на одних и тех же минутах.

| Модель | log loss | AUC |
|---|---|---|
| константа (доля ударов) | 0.6021 | 0.500 |
| v0, веса мокапа | 0.5976 | 0.561 |
| **v1** | **0.5970** | **0.566** |
| все веса, подобранные заново на каждом блоке | 0.5970 | 0.566 |

**Выводы.**
- **Flow предсказывает удары:** v1 лучше константы, выигрыш в log loss 95% [0.0030, 0.0073]. Сигнал скромный (AUC 0.57). Flow показывает текущее давление, а не гарантирует удар, и так его и надо подавать.
- **Полный подбор весов не лучше v1:** 95% [−0.0008, 0.0007]. Три правки v1 взяли от подбора всё, что он может дать.
- **Устойчивые веса** (одинаковые на всех пяти блоках) вошли в v1: ключевая передача (+7…+16), удаление (−22…−26), замена (+5…+13). Неустойчивые (жёлтая, отбор, обводка) оставлены как есть.
- На одной отложенной четверти сезона (95 матчей) интервал задевал ноль. Сигнал такого размера видно только на всём сезоне, поэтому проверка сделана перекрёстной.

**Что не подбирается и почему.**
- `τ` и `r` — это определение momentum. Если отдать их подбору, `τ` уходит к 20 минутам: длинная память лучше предсказывает удары, потому что измеряет, кто вообще сильнее, а это уже не momentum.
- Наклон `b` берётся по текущим весам и фиксируется. Иначе подбор сжимает все веса к нулю и увеличивает `b`: прогноз тот же, а Flow на экране почти не двигается.
- **Гол остаётся +23.** Данные дают гол от −1 до −13: после гола забившие отходят назад и бьют меньше (эффект счёта). Но Flow отвечает на вопрос «кто давит», и метрика, падающая после гола, читалась бы как ошибка. Это решение продукта, а не данных.

**Оговорка.** Правки v1 выбраны по тем же блокам, на которых потом измерены, поэтому оценка v1 слегка оптимистична. Строка «подобранные заново» не имеет этой проблемы, и её результат тот же.

**Как повторить.** `python ai/calibration/download.py`, затем `go run ./cmd/export` в `services/` и `python ai/calibration/fit.py` (около 10 минут).

## 9. Решённые вопросы

| Вопрос | Решение |
|---|---|
| Учитывать ли владение | Да: слагаемое `w_p · (p − 0.5)` за каждую минуту, для ESPN владение восстанавливается из нарастающего итога (разделы 2 и 3) |
| Что делать с перерывом | Затухание стоит, в начале второго тайма импульс умножается на `r = 0.7` (раздел 3.1) |
| Flow падал в 0 у команды без мяча | Импульс не уходит ниже нуля, плюс фоновый `S₀ = 3`: Flow не ниже ≈15 (раздел 3) |
| Предсказывает ли Flow что-нибудь | Да, удары в ближайшие 10 минут, значимо лучше константы на 380 матчах; веса v1 (раздел 8) |
